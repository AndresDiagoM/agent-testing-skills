# Why test-gate and pgtap-rls exist

## The incident
On 2026-11-12 a coding agent acting as a quality gate spent **1 h 41 min** on an end-to-end suite whose tests take about **2 minutes**. Every test signed in through the UI (~70 sign-ins), the local Supabase auth limit is 30 sign-ups or sign-ins per 5 minutes per IP address (the default of the Supabase CLI [`config.toml`](https://github.com/supabase/cli/blob/d8f66a08d1/apps/cli/src/shared/init/testdata/templates/config.toml), `sign_in_sign_ups = 30`), and the agent split the suite into five batches with `sleep 320` between them, re-running the full suite after each fix. After fixing the cause (sign in once with a Playwright setup project and `storageState`), the full suite ran in 117 s with ~15 sign-ins.

Nine more incidents from the same day (tests clicking before hydration, specs that were never run, stale servers, Windows browser stalls, test doubles drifting from the real database, a fake secret flagged by scanners) shaped the rules in these skills. The incidents and the Windows measurement come from the author's own runs on one project and one Windows machine; they are not claims about the projects below.

Every project below may have changed since, and "not covered" means "not found in the files we read at that commit", not "does not exist anywhere in the project".

### Existing pgTAP skills
We first wrote that no pgTAP skill existed. That was wrong. A search of GitHub and skills.sh on 2026-11-12 found, among others:

- [`github/awesome-copilot` `supabase-rls-policies`](https://github.com/github/awesome-copilot/blob/e593e6649d3b538772b7329b26bcd626b54900ff/skills/supabase-rls-policies/SKILL.md): helps write policies well (a `to` clause on every policy, the owner bound in `with check`, `user_metadata` versus `app_metadata`, `security_invoker` views, an MFA restrictive policy, indexes, `security definer` functions) and includes a two-user pgTAP template with an `anon` case, unfiltered UPDATE/DELETE probes, an owner-transfer case, claims for `aal` policies and a temporary `using (true)` check.
- [`nghiahsgs/taw-kit` `testing-rls-pgtap`](https://github.com/nghiahsgs/taw-kit/blob/9cfb26af52/skills/testing-rls-pgtap/SKILL.md): detects tables and policies from migrations and writes pgTAP tests.
- Project-specific pgTAP skills such as [`giswater/plugin`](https://github.com/giswater/plugin/blob/b9011c2b9a/.agents/skills/giswater-pgtap/SKILL.md), [`Jayaprakash7777/simplin-erp-website`](https://github.com/Jayaprakash7777/simplin-erp-website/blob/6dfef1f278/.agents/skills/pgtap-testing/SKILL.md) and [`imbhargav5/nextbase-nextjs-supabase-starter`](https://github.com/imbhargav5/nextbase-nextjs-supabase-starter/blob/00ad2da857/.agents/skills/nextbase-database-testing/SKILL.md).

`pgtap-rls` is therefore one more option, not the first, and it is meant to be used next to `supabase-rls-policies`, not instead of it. That skill helps you write policies; `pgtap-rls` proves them across the schema. What it adds is listed in its [README](../plugins/pgtap-rls/README.md): a script that builds the mutated copy for the mutation check (policies and grant denials), catalog-wide RLS coverage, pinned policy sets, per-role claims including `service_role` as a setup role, function checks read from the catalog, unique ids per file, the shared evidence file and a client-level sign-in template. Three test patterns in `pgtap-rls` 0.3.0 come from the `supabase-rls-policies` file at commit [`e593e6649d`](https://github.com/github/awesome-copilot/blob/e593e6649d3b538772b7329b26bcd626b54900ff/skills/supabase-rls-policies/SKILL.md): unfiltered UPDATE/DELETE probes, the owner-transfer case, and full claims at every switch for policies that read `auth.jwt()`.

## What these skills add
1. **One full run per gate** with a time cap per step (test-gate).
2. **Supervision of other agents:** stop on sleeps, batches and repeated full runs; the reviewer re-runs the gates (test-gate).
3. **Fixer discipline as a check, not advice:** no retries, `fixme`, `skip`, broader locators or longer timeouts; a skip needs approval and appears in the evidence (test-gate, `e2e-guard`).
4. **Windows:** two or more Playwright-bundled Chromium processes stalled requests in 10 s steps on the author's machine; use the installed Chrome (test-gate).
5. **Auth rate limits:** sign in once, per-spec users, fix the cause (test-gate).
6. **Machine-readable evidence:** `.gate/last.json` with command, exit code, duration, counts and failing tests (test-gate, shared with pgtap-rls).
7. **Database tests and doubles parity:** allow and deny per role, silent denials, a scripted mutation check, functions and grants, and the evidence file (pgtap-rls; several of these ideas are also in the Supabase docs and the skills listed above).
8. **Portability:** plain SKILL.md for Claude Code, Codex, opencode and Antigravity; commands read from `package.json` instead of hard-coded `npm`/`npx` (both).

## Design choices
- `SKILL.md` under 5 KB with the always-on rules; topic references load only when needed.
- One recipe per topic, so the skill never contradicts itself.
- Every version-dependent tip says which version it was checked against.
- No secrets in examples, not even fake ones, and no destructive commands.
- Repo rules win: the `OVERRIDES.md` pattern lets a repo correct a third-party skill without forking it.
